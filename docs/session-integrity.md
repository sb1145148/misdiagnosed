# 会话存储完整性

会话数据看起来完好、实际读不出来的一类坑。

---

## 6. 会话文件在磁盘上，但界面里"消失了"

**现象**

```console
$ ls -l ~/.dsh/sessions/<workspace>/session-<id>/session.v4.jsonl.zstd
-rw-------  ...  17M  session.v4.jsonl.zstd
```

文件在、能解压、解出来的每一行都是合法 JSON。
但对话列表里**没有它**，也不弹任何提示。

日志里只有一行容易被略过的话：

```
corrupt Zstandard session log: first frame is not exactly one header line
```

**判断信号**

```bash
python3 scripts/frame-check.py ~/.dsh/sessions
```

输出里出现 `首帧 N 行（应为 1）` → 就是这个坑。
全部是 `首帧不合规 0 个` → 不是它，往索引/权限/版本方向查。

**根因**

读取器要求**第一个 zstd 帧只装一行**（头部）。

这样"只看头部"时不用解压整个文件——只解第一帧就够。

任何把整份内容压成**一个帧**的工具都会破坏这个约束：

```bash
zstd -q -f -o out.zst in        # ← 整份一个帧，首帧变成几千行
```

判定失败的后果是**静默跳过**：文件保留、不报错、不出现在列表里。

**解法**

重新分帧，第一帧只装头部那一行：

```python
frame1 = compressZstd(header_line)     # 首帧：恰好一行
frame2 = compressZstd(rest_of_body)    # 正文：另起一帧
```

**不要**用 `zstd -o` 直接重写会话文件。要重写就自己切帧。

**代价**

文件看起来完全健康，所以排查方向会跑到"索引坏了""版本不对""权限问题""备份没还原全"上去。
实际是格式问题，跟那三样都无关。

**适用边界**

只在"首帧必须一行"这种读取器上成立。普通 zstd 文件随便怎么压都能读，
所以拿通用压测工具验证是**验证不出来**的。

## 7. 改目录名，让整个工作区一起挂掉

**现象**

```
对话列表空掉
「打开文件夹」失败
插件状态里 WorkspaceController / SessionController 一直 pending
```

而单独看每个会话，文件都在、都能解压。

**判断信号**

```bash
python3 scripts/frame-check.py --identity ~/.dsh/sessions
```

输出 `目录名 ... ≠ header id ...` 或 `工作区目录 ... ≠ --...--` → 就是这个坑。

**根因**

存储层用头部里的 `id` 和 `cwd` **反推**「这个会话应该在哪个路径」，再和实际路径比对：

```
sessions/--<cwd 里的 / 换成 ->--/
        session-<id>/
```

推导结果和实际不符 → 判为损坏 → **注册表加载失败** →
依赖注册表的服务（列表、工作区、调度）全部停在 pending。

**目录名是结构性信息，不是标签。**

**解法**

改回来：

```bash
cd ~/.dsh/sessions
for d in */*.disabled; do
  [ -d "$d" ] && mv "$d" "${d%.disabled}"
done
```

要"移出"某个会话，就搬到 `sessions/` **外面**——扫描不到，就不会参与校验：

```bash
mkdir -p ~/.dsh/_quarantine
mv ~/.dsh/sessions/--<slug>--/session-<id> ~/.dsh/_quarantine/
```

**不要** `mv xxx xxx.disabled`。

**代价**

实测复现过。原来的问题是"某个会话报错"，改完变成**所有对话都打不开**。
一个"整理一下"的动作，把可用状态弄成了不可用。

**适用边界**

只对"路径由内容推导"的存储成立。普通目录随便改名无所谓，
所以凭直觉判断"改名又不影响内容"会踩中。

## 8. 备份每次都成功，但永远导不进去

**现象**

```console
$ # 备份
✅ 备份完成，1234 个条目
$ # 导入
❌ ARCHIVE_LINK_ESCAPE
```

修掉这个之后，还会依次冒出 `PLUGIN_SYSTEM_PROFILE_MISSING`、`TARGET_CHANGED`。

**判断信号**

```bash
tar -tvzf backup.tar.gz | awk '$1 ~ /^l/ {print $NF}' | grep -E '^(/|\.\./)'
```

只要有输出（存在绝对路径软链，或以上级目录开头的软链）→ 就是这个坑。

**根因**

**打包端和恢复端用了两套合法性定义：**

- 打包端只校验链接**格式**（非空、长度、不含 `\0` 和 `\`）
- 恢复端校验链接**可达范围**（不能跳出根目录）

依赖管理工具会把本地依赖建成相对软链：

```
node_modules/some-pkg -> ../../../../deps/some-pkg
```

打包时原样收进去，恢复时被判为越界 → **整个恢复中止**。

更麻烦的是：这类条目在恢复时**本来就会被删掉重建**，
归档里那一份对恢复毫无用处——但它足以让整个包作废。

**解法**

按改动成本从低到高：

1. **打包阶段跳过**指向归档外的链接（标成 `EXCLUDED` + `reason`），不打包
2. **恢复端降级**：遇到越界链接只记警告、保留元数据，不中止
3. 如果只能改依赖方式：把相对软链换成正本，别让链接存在

**代价**

备份文件看起来完好——能解开、条目数正常、字节数正常——
所以会以为是"导入功能坏了"，而不会想到"备份里带了不该带的东西"。

**适用边界**

绝对路径软链和相对路径软链的处理**可能不同**（前者更容易被容忍）。
按现象判断时要分别看，不要只测一种。

---

## 附：这三条的共性

它们都满足同一个模式：

```
看起来是 A 坏了  →  实际是 B 的形状不对
```

而 A 和 B 之间没有直接的因果关系，所以凭直觉排查一定跑偏。

**判断它们的成本都极低（一条只读命令），
误判的代价都极高（几小时到"数据永久导不进去"）。**
