# 数据口径

**这一类坑最坏的地方是：数据全对，结论全错。**

---

## 5. 把「采集轮次」当「自然日」

**现象**

文章里写着「第 13 天」，但实际只观察了 9 天。

**判断信号**

```bash
scripts/timezone-check.sh --days
```

或者手工：**检查同一日期是否对应多个「第 N 天」**。

```
7.12  第七天（10-25）
7.13  第八天（10-25）   ← 同一天，两个编号
7.14  第九天（10-25）   ← 同一天，三个编号
```

**根因**

数据是**随机时间抓的**，一天可能采两三次。
作者按「一次采集 = 一天」编号，天数和真实日期脱钩。

**解法**

- 标题一律写「**第 N 天（MM-DD）**」双标注，不写裸的「第 N 天」
- 同一天多次采集只算一个自然日，差异写成「当天 3 次采样的区间」
- 早期按轮次写的叙述，改称「第 N 轮」而不是「第 N 天」

**代价**

虚高 4 天。所有结论的数字没错，但**节奏感是错的** —— 读者以为观察了 13 天，
实际是 9 天里高密度采样。

**适用边界**

任何时候做「连续观察」类数据都适用。**采集频率和统计口径必须分开定义。**

## 6. 把累计值当首日值

**现象**

- 刚发布的视频「暴跌」
- 三周前的旧视频「突然涨了」

**判断信号**

```bash
# 同一个接口，看有没有「时间维度」
curl -s '.../view?bvid=xxx' | grep -o '"pubdate":[0-9]*'
```

如果拿到的 `play` 是**累计值**，而你没减去时间维度：

```python
play_per_hour = play / (now - pubdate) * 3600   # ✅ 归一化
play_raw      # ❌ 直接比大小会把「刚发的」判成「暴跌」
```

**根因**

播放量是**从发布到现在的累计数**。刚发 10 分钟和发了 3 天放在一起比，没有意义。

**解法**

- 算「地板」（稳定的低位）时，**只统计发布超过 24 小时的作品**
- 或者用「每小时播放」归一化后再比

**代价**

一次结论算反：差点写「头部账号已经衰减」，实际是刚发的视频还没跑起来。

**适用边界**

所有累计型指标：播放、阅读、Star、下载量。
**做趋势分析前先问：这个数是存量还是增量？**

## 7. 容器 UTC 写进 +08 的报告

**现象**

报告里所有时间都差 8 小时，或者「凌晨 3 点发的内容」其实发生在上午 11 点。

**判断信号**

```bash
date -u
date
python3 -c "import datetime;print(datetime.datetime.now(), datetime.datetime.now(datetime.timezone(datetime.timedelta(hours=8))))"
```

两个输出一样 → 容器就是 UTC。

**根因**

`datetime.fromtimestamp()` 默认用**容器本地时区**。容器是 UTC，人和平台是 +08。

**解法**

```python
TZ = datetime.timezone(datetime.timedelta(hours=8))
datetime.datetime.fromtimestamp(ts, TZ)
```

**代价**

时间线全错位。更隐蔽的是：**数据本身没错，只是排序和归天会错**。

**适用边界**

跨时区抓数据、跨时区写报告时必查。容器 / CI / 服务器默认多数是 UTC。
